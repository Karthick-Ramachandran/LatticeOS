---
title: Safe initialization
description: Plan or create the small committed LatticeOS configuration file.
---

`lattice init` sets up the configuration location without touching application source. It owns one
committed file: `.lattice/config.json`.

```json title=".lattice/config.json"
{
  "schemaVersion": 1
}
```

The file is intentionally small. It reserves a stable configuration location and schema version; it
does not yet change analysis behavior. A later setting for roots, exclusions, thresholds, or output
limits needs its own schema decision and validation before LatticeOS reads it.

## Commands

```bash title="Plan the first write"
lattice init
# Would create .lattice/config.json. Run lattice init --write to create it.
```

Planning is the default. It does not create `.lattice`, the config file, a cache, or an application
file.

```bash title="Create the missing config"
lattice init --write
# Created .lattice/config.json.
```

If the config already exists, LatticeOS leaves it unchanged.

```bash title="Replace an existing config explicitly"
lattice init --write --force
```

`--force` without `--write` is a usage error. `--dry-run` is an explicit spelling of the default and
cannot be combined with `--write`.

Every form accepts `--root <path>` and `--json`. JSON uses the normal schema-versioned CLI envelope.
For example, a first-run plan has this result payload:

```json title="lattice --json init"
{
  "action": "create",
  "mode": "dry-run",
  "path": ".lattice/config.json"
}
```

## Safety boundary

ADR-0014 assigns configuration inspection and writes to `RepositoryRoot`. The CLI never accepts a
destination path. The repository authority checks `.lattice` and `config.json` for regular,
in-root paths, rejects symlinks, creates the directory only during a real write, and uses a temporary
sibling. The normal no-force creation uses an exclusive link so a concurrently created file is
skipped instead of overwritten; explicit force uses atomic rename.

No init path reads or executes consumer source, configuration, environment files, or a network
service. The config file cannot contain secrets under the Phase 1 security model.

## Test evidence

Focused analyzer tests cover missing, created, existing, forced, and symlinked configuration paths.
CLI tests cover human and JSON plans, opt-in writes, skip-existing, force, source preservation, and
invalid force usage.

```bash
pnpm --filter @latticeos/analyzer test
pnpm --filter @latticeos/cli test
```

- The only init target is `.lattice/config.json` with the schema-version-1 floor shown in this guide.

- `RepositoryRoot` is the only authority for config inspection and writes. The CLI must not accept a

  temporary-file cleanup, and explicit force behavior.
- Do not read or execute consumer source, config, environment files, or remote services.
- Do not make unimplemented config fields appear active. A behavioral config schema needs a new ADR,
  validation, fixtures, and a security review.
