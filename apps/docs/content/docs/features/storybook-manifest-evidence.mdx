description: Attach a local Storybook example only when its generated manifest and React import agree.

<Callout title="Implemented" type="info">
  LatticeOS reads one bounded, locally built Storybook components manifest. It never starts
  Storybook, opens a development server, or executes `.storybook` configuration.
</Callout>

Storybook is optional. Without a manifest, LatticeOS keeps the normal React, Tailwind, and shadcn
result. It reads the fixed path `storybook-static/manifests/components.json` only after project
detection finds Storybook. The generated directory is excluded from normal repository discovery, so
its bundles never enter React or Tailwind analysis.

## What it records

The adapter accepts the current React components-manifest subset produced by Storybook: a top-level
`components` object with an entry name, a repository-relative `*.stories.*` path, and named stories.
It does not use descriptions, prop documentation, snippets, imports, or absolute paths from the
manifest.

LatticeOS attaches a `story` record to a React component only when all of these are true:

- the manifest's story path is an admitted React source file;
- the story file has a non-type-only import that React analysis resolved to a component; and
- that component's display name matches the manifest component name.

The result is `corroborating` `manifest` evidence. It confirms that the local generated manifest
lists a named Storybook example for a component. It does not prove a rendered result, runtime
behavior, product meaning, or that the component fits every task.

```ts title="Direct static adapter input"
import { analyzeStorybook } from "@latticeos/adapter-storybook";

const result = analyzeStorybook({
  manifests: [{ path: "storybook-static/manifests/components.json", content: manifestText }],
  components: reactAnalysis.components,
  imports: reactAnalysis.imports,
});
```

`analyzeProject` runs this bridge after React and shadcn analysis. The attached evidence is available
to CLI search, inspect, and context output through the normal Reuse index.

## Bounds and unsupported forms

The bridge reads one fixed local file, up to 1 MiB by default. It accepts at most 1,000 component
entries and 100 stories per component. All limits have hard caps. A missing manifest is ordinary
optional-tool absence. An oversized, unreadable, malformed, changed, or unmappable manifest returns
bounded diagnostics and leaves existing component evidence usable. The dedicated reader rejects a
symlink at every segment of the fixed manifest path.

Storybook documents the rich [components manifest](https://storybook.js.org/docs/ai/manifests) as a
preview API. LatticeOS supports only the named fixture shape at the conventional built path. Custom
output directories, dev-server URLs, ref-based manifests, package-local or external story paths,
name-only mapping, and arbitrary manifest paths are not supported. The adapter makes no network,
MCP, registry, package-install, telemetry, or source-execution call.

The `fixtures/next-workspace` manifest maps its `Button` entry through the real
`button.stories.tsx` import. Direct and analyzer tests cover deterministic output, malformed data,
unmapped entries, type-only imports, missing manifests, byte bounds, static-directory exclusion, and
a valid Reuse index after optional evidence fails.

```bash
pnpm --filter @latticeos/adapter-storybook test
pnpm --filter @latticeos/analyzer test
```
